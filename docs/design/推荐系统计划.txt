推荐系统模块化重构详细方案
1. 目标与原则
本次是“等价重构”，不调整推荐算法、权重、HTTP 接口、状态文件格式和生产开关。
核心目标：
将候选生成、排序、反馈、观察、学习、调参、状态存储分离。
消除反馈模块和调参模块之间的循环依赖。
异步请求链不再直接执行同步磁盘 I/O。
反馈、状态文件和 JSONL 日志具备并发安全性。
保留旧模块作为兼容入口，现有调用方不需要一次性全部修改。
当前已经取消的显式反馈按钮保持取消，不得在重构中恢复。
不扩大到整个 proactive_chat/service.py、生成模块或前端架构。
新包使用 main_logic/recommendation/，不使用 main_logic/proactive_recommendation/，避免与现有 proactive_recommendation.py 兼容文件产生导入歧义。

3.4 通用存储
storage/atomic_json.py 提供：
class AtomicJsonStore:
    def read(...)
    def write(...)
    def update(...)
    def delete(...)
要求：
使用现有依赖 portalocker。
锁定独立的 文件名.lock，而不是正在替换的目标文件。
update() 在同一把锁中完成“读取—修改—写入”。
临时文件名包含 PID 和线程 ID，避免多个线程共用 .tmp。
写入完成后使用 os.replace() 原子替换。
状态文件内容、字段、版本保持不变。
storage/jsonl.py 提供：
class JsonlStore:
    def append(record, *, sanitizer, rotate_bytes) -> bool
    def load(*, sanitizer, limit=None) -> list[dict]
要求：
旋转和追加必须处在同一把跨线程、跨进程文件锁中。
保留 .1 轮转规则和 10 MB 默认大小。
一次 API 反馈仍记录一条原始事件；并发去重只针对学习状态，不擅自丢弃原始事件。
遇到损坏行继续跳过，保持现有容错行为。

3.9 应用层
application.py 是 Router 和领域模块之间唯一的业务入口：
class RecommendationApplication:
    async def create_turn(...)
    async def record_feedback(command)
    def record_feedback_sync(command)
    async def build_summary(query, *, config_dir)
    async def get_preference_state(...)
    async def reset_preference_state(...)
    async def get_tuning_status(...)
    async def reset_tuning(...)
    async def pause_tuning(...)
    async def resume_tuning(...)
    def get_runtime_status(...)
    def rollback_runtime(...)
同时提供：
def get_recommendation_application() -> RecommendationApplication
返回进程级单例，确保所有入口共享同一个 PendingFeedbackRegistry。
record_feedback() 的应用层顺序：
在线程池中执行完整反馈事务。
若事件确实写入日志，再调用 TuningService.maybe_auto_apply_from_logs()。
FeedbackService 本身不知道 TuningService，循环依赖因此消失。
build_summary() 负责并发读取观察和反馈日志，再调用纯报表模块组装现有响应。Router 不再自行拼接十多个报表。
3.10 Turn 生命周期
turn.py 提供 RecommendationTurn：
class RecommendationTurn:
    @classmethod
    async def create(...) -> RecommendationTurn

    def decide_source(...) -> None
    def decide_material(...) -> list[tuple[str, str]]
    async def finalize(response_body) -> None
create()：
一次性记录统一的 now。
使用 asyncio.to_thread() 加载 feedback、preference、bandit、tuning 状态。
可独立的加载任务通过 asyncio.gather() 并行执行。
preference 的 legacy 初始化在 feedback snapshot 完成后执行。
tuning adjustment 缓存在 Turn 中，_context() 不再读取磁盘。
recent_sources 由 proactive_chat 调用方传入，推荐包不反向导入聊天模块。
decide_source()、decide_material() 保持同步，因为它们是纯内存计算。
finalize()：
在线程池中构造、脱敏和写入 observation。
写入后注册 pending feedback。
更新进程内 shadow history。
不把日志失败扩散为主动聊天失败，继续保持 fail-soft。
生产调用修改为：
recommendation_turn = await recommendation_app.create_turn(...)
...
await recommendation_turn.finalize(body)
history.py 负责现有 shadow history：
record_shadow_selection()
recent_shadow_sources()
recent_shadow_candidate_ids()
内部使用锁保护多请求访问。

强制规则：

6. 实施顺序
阶段一：锁定当前行为
以当前已取消显式反馈 UI 的工作区为基线。
运行现有 763 项 proactive 单元测试、两个前端测试、Ruff 和语法检查。
不恢复已经删除的按钮配置、翻译和前端事件监听。
阶段二：存储和并发安全
落地 AtomicJsonStore、JsonlStore 和 PendingFeedbackRegistry。
preference、feedback state、bandit、tuning 先迁移到新 Store。
增加线程并发测试，确认一个反馈 turn 只产生一次学习更新。
原始日志仍按实际收到的 API 事件逐条保存。
阶段三：拆分 feedback、observation、tuning
先移动纯函数，再移动 Store，最后移动 Service。
应用层接管“反馈成功后触发自动调参”。
删除 feedback 中对 tuning 的局部导入。
旧模块同步改为兼容导出。
阶段四：拆分 engine 和 Turn
拆候选生成、评分、决策、active bias、observation builder。
引入异步 RecommendationTurn.create() 和 finalize()。
修改主动聊天生命周期中的两个调用点。
保证固定输入下候选 ID、分值、顺序和 observation 内容不变。
阶段五：Router 变薄及清理
反馈接口转为 RecommendationApplication.record_feedback()。
summary 接口转为 build_summary()。
preference、runtime、tuning 接口只做 HTTP 校验和应用层调用。
添加架构依赖测试，防止重新形成循环依赖。
更新设计文档中的最终目录与依赖方向。

8. 验收标准和默认约束
现有 763 项 proactive 测试继续通过，并通过新增并发和架构测试。
HTTP 接口、状态文件和推荐输出无行为变化。
同一反馈 turn 在并发请求下最多更新一次对应学习证据。
JSONL 日志无交叉写、损坏行或轮转竞争。
主动聊天异步主路径不直接执行文件读写。
feedback 与 tuning 之间不存在直接或局部循环导入。
所有旧导入路径继续有效。
单个业务模块原则上控制在 800 行以内；报表复杂文件允许接近 900 行，但不得重新混入存储或状态更新。
不创建 utils.py、helpers.py 等职责不清的文件；私有函数放在其唯一调用者所在模块。
当前工作区已有未提交修改，重构必须在其上增量进行，不覆盖用户修改。
实施会新增和调整测试文件；按照仓库指令，后续若要求创建 commit，必须先单独确认是否允许提交这些测试变更，不能自动提交。
